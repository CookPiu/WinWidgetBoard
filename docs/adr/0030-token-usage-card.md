# ADR-0030：纳入 Token 用量卡片，按厂商分别解析本机会话记录

状态：Accepted
日期：2026-08-28
关系：修改 [ADR-0022](0022-lightweight-core-strategy.md) 的「核心项」结论（新增一项）；沿用
[ADR-0018](0018-provider-host-and-card-snapshot-boundary.md) 的 Provider 与快照边界；
沿用 [ADR-0020](0020-open-meteo-weather-provider.md) 「读数不落库」的处置方式

## 背景

用户希望在面板里看到各厂商、各模型的 token 消耗，包含可读的报表、实时更新的速率，
以及在卡片内切换总览与单个厂商。当前要求覆盖 Claude 与 Codex。

先评估过做成插件：现有架构不支持第三方插件，卡片目录、模板选择和 Provider 注册全部是编译期常量，
没有任何动态加载路径。补齐真实插件平台需要包格式、签名信任、沙箱、权限执行点和声明式 UI 五个子系统，
门禁见 [ADR-0004](0004-plugin-security-boundary.md)。为一张自用卡片投入该平台不成比例，用户据此放弃插件路线。

[ADR-0022](0022-lightweight-core-strategy.md) 要求任何范围恢复都需明确再批准，本 ADR 是该批准的记录。

实测参考机（Windows 11 26200）上的四条事实决定了方案形状：

- 用量数据已在本机：两家都把 token 计数写进自己的会话记录，含计数、模型名与时间戳；
- **同一次调用都会被重复记录，但形式不同**。Claude 每个 content block 写一行且各自重复整个
  `usage`，参考机上 6905 行只对应 3660 次真实响应（47% 是重复）；Codex 的同一轮会被后续
  `token_count` 事件反复上报，求和 `last_token_usage` 得到的是会话总量的 1.4～2.1 倍；
- **两家都没有任何耗时字段**，没有 duration、latency 或首 token 时间；
- **只有 Codex 发布配额**：`rate_limits` 里有滚动窗口已用百分比、窗口长度、重置时间与 credits 余额。

## 决策

### 1. 范围

核心项新增「Token 用量」，卡片类型 `builtin.tokenusage`。
这不重新开放计时器、待办、剪贴板、日历、插件、账号与云同步。

### 2. 数据来源只有本机会话记录，不接任何计费 API

不调用各供应商的用量或计费接口。因此**不需要 API key、账号或任何网络访问**，
Provider 的 `requiresNetwork` 为 false。代价是拿不到代理才能看到的 HTTP 状态码与延迟，这两列本卡片不提供。

当前支持两家，各自的记录格式与口径完全不同：

| 厂商 | 位置 | 计数字段 | 去重键 |
| --- | --- | --- | --- |
| Claude | `%USERPROFILE%\.claude\projects\*\*.jsonl` | 每行一份完整 `usage` | `(requestId, messageId)` |
| Codex | `%USERPROFILE%\.codex\sessions\**\*.jsonl` | 会话累计 `total_token_usage` | 文件路径 + 增量序号 |

Codex 的 `archived_sessions` 不读：那是可被整体重写的历史记录，且其中没有落在一天窗口内的内容。

### 2.1 Codex 必须用累计量差分，不能求和 `last_token_usage`

每个 `token_count` 事件同时带该轮的 `last_token_usage` 和会话累计 `total_token_usage`。
**求和后者是错的**：同一轮会被后续事件重复上报，参考机上求和结果是会话总量的
1.4 倍（input）和 2.1 倍（output）。累计量实测单调不减，因此取相邻事件之差作为增量。

累计量下降视为会话被压缩，该次读数作为新基线，不产生负增量。

Codex 事件本身不带模型名，模型由 `turn_context` 声明并对其后的 `token_count` 生效。
Codex 的 `input_tokens` 内含缓存读取，记录里拆开，使两家的"计费量"含义一致。

Codex 记录的身份是**文件路径 + 增量序号**。必须能从文件本身复现——
早期实现用每次读取新生成的 GUID 作前缀，导致截断重读被当成新记录重复计数。

### 2.2 配额只读不算，且过期即不显示

Codex 在 `rate_limits` 里发布真实配额：滚动窗口的已用百分比、窗口长度、重置时间戳与 credits 余额。
Claude 的转录没有任何对应字段，因此**只有 Codex 页显示配额区块**，
总览页不显示——并列会让人以为 Claude 那边也在统计。

配额读自会话记录而非查询，因此它的新旧程度等于最后一次会话活动。由此两条约束：

- 快照带自己的观测时间，卡片显示"截至 HH:mm"；
- **重置时间已过去的窗口一律不显示**。它必然已经重置，而重置后用了多少本卡片无从得知，
  显示一个陈旧的"已用 100%"比什么都不显示更糟。credits 不随窗口重置，因此保留。

### 3. 去重是正确性要求，不是优化

两家都必须做，键不同：

- Claude 按 `(requestId, messageId)` 去重。两半都用：只用 messageId 会把一次真实重试合并掉，
  只用 requestId 会漏掉缺该字段的行。不去重会让用量虚高近一倍；
- Codex 见 2.1，用累计量差分而非去重重复行，但截断重读仍靠可复现的身份由去重兜住。

去重键含厂商 ID：两家的 ID 空间互不相关，否则可能碰撞。

`<synthetic>` 模型的记录一律排除——它带 usage 但从未计费。

### 3.1 卡片分页，设置只管启用哪些厂商

卡片分为总览页和每个已启用厂商各一页。总览按厂商拆分，厂商页按模型拆分。
两家不可互换——Codex 有配额而 Claude 没有——单一合并视图要么丢掉配额，要么暗示它覆盖两家。

只有一个厂商时不显示页签：总览会与那一页完全重复。

卡片以**当日花费为主视觉**，其余为读数行，每个 token 类型带自己那一份金额而不是各自重复总额。
不展示速率与模型占比：卡片高度有限，用户关心的是各项计费、订阅余额与用量，
速率与占比属于报表窗口（尚未实现）的内容。

当前页是**面板内视图状态**，不落盘、不走 IPC，每次打开面板都回到总览。

设置面只提供**启用/禁用厂商**。记录位置不可配置——每家都写在用户目录下一个固定位置——
加路径输入框会把两个复选框变成一个校验面，去应对一个尚不存在的场景。
已启用但本机无记录的厂商仍可保持开启（之后安装了就自动开始统计），设置页标注"无记录"。

关闭某厂商时立即丢弃其记录并重置其水位，而不是等它自然过期。

### 4. 速率只按墙钟窗口测量，不伪造单次响应速度

转录没有耗时字段，所以"上次响应的 tokens/s"只能用相邻时间戳之差近似，
而那段间隔里包含用户思考时间和全部工具调用，会严重失真。因此不提供该指标。

提供两个速率，**窗口长度相同（15 分钟）且统计范围同为今日**：

- `usage.rate.current`：最近 15 分钟的计费 token 除以 15；
- `usage.rate.peak`：今日最忙的 15 分钟。

峰值曾按小时平均，导致"当前"读数是"峰值"的 8 倍——那是两个分母的假象而非真实事件。
峰值也曾覆盖整个保留窗口，导致一个今天毫无用量的厂商页出现"今日为空、峰值 32.5K/min"的并列，
两个数都对，放在一起无法阅读。同尺度、同范围是这两个数能并列的前提。

### 5. 计费总量排除缓存读取

`billed = input + output + cache_creation`。缓存读取比其余三项之和大一个数量级
（参考机 11M vs 400K），并入总量会让所有会动的部分消失。缓存读取作为独立指标单独显示。

### 6. 会话记录的内容绝不进入本进程

这些文件里是完整对话——源码、路径、可能的密钥片段。因此：

- 解析用 `Utf8JsonReader` 逐 token 走，`content` 数组按子树 `Skip()`，**不反序列化、不构造字符串**；
- 落盘的只有"启用了哪些厂商"这一项设置，不含任何用量数字；
- 每条记录只留四个计数、模型名、身份对和时间戳；
- 这些聚合结果**不写入 SQLite**，只存在于 broker 进程内，与天气读数的处置一致
  （[ADR-0020](0020-open-meteo-weather-provider.md)）；
- 解析失败只累加一个计数器，不记录任何来自对话的内容。

### 7. 增量读取，且只推进到完整行

两家的记录都是 append-only 且正被另一进程写入，这部分逻辑完全相同，因此共用一个增量读取器
（`IncrementalJsonlReader`），各厂商只提供自己的解析。具体约束：

- 每个文件保留字节水位，只读新增部分；
- 以 `FileShare.ReadWrite | Delete` 打开，否则最该读的那个文件必然打不开；
- 水位只推进到**最后一个完整行**之后，半行留给下一次；
- 文件变短视为被截断或重建，整份重读，由去重兜住重复；
- 单行超过 4 MiB 视为不可解析并跳过，与 IPC 帧上限同一思路。

### 8. 卡片不可见时完全不读盘

`hiddenInterval` 为 null。与硬件监控不同，本卡片没有任务栏消费者，面板关闭时无人需要读数。
若暂停时间超过保留窗口导致记录全部老化，下一次 tick 会重置水位整份重读，使长时间暂停可自愈。

### 9. 费用估算：只报公开价，且宁可少报也要说明少报

原门禁要求先确定价格表的来源与更新方式，并在 UI 标注为估算。三者的落法：

**来源**：Claude 侧取 `platform.claude.com/docs/en/about-claude/pricing`（基础输入、5 分钟与
1 小时缓存写入、缓存命中、输出五档）；Codex 侧取 OpenAI 2026-08-22 降价后的 GPT-5.6 公开价，
其缓存写入按未缓存输入的 1.25 倍、缓存读取按其公布的 cached input 价。
价表带 `VerifiedOn` 常量，核验日期是数据的一部分而不是注释——价格会变，
过期是这里可预期的失效方式。

**不做家族匹配**：查表是精确匹配。经路由改写的模型 ID（如 `anthropic/claude-opus-5-ps-aws-dst`）
虽然包含 `claude-opus-5` 子串，但是否按一方价计费无人核实过，按子串猜等于给一个没人验证的假设配上确定的数字。

**无价模型不计入，并且报数**。把未知模型按 0 计价会让总额静默偏低，
而偏低的总额是唯一无法靠观察发现的错误。因此这类模型的 token 照常计入用量，
金额不计入，并在界面上以 `+` 后缀表示该金额是下限而非总额。

**标注为估算**：金额前缀 `≈`；完整措辞放在设置页说明里——两个工具通常是订阅制，
每 token 单价并不是用户实际支付的价格，这个数字与 ccusage、cc-switch 报的是同一种
「按 API 价折算」的量。此外金额涵盖全部 token 类型（含缓存读取），
而并排的 token 数按第 5 节口径不含缓存读取，这一差异同样在设置页说明。

**缓存写入必须按时长分档计价**。转录里的 `cache_creation` 区分
`ephemeral_5m_input_tokens` 与 `ephemeral_1h_input_tokens`，两档价差 60%（1.25 倍对 2 倍）。
参考机实测当日缓存写入 100% 落在 1 小时档，按 5 分钟档计会少收约 5%。
缺少该字段时按 5 分钟档计——两者中较低的一档，宁可低估也不虚报。

## 理由

- 数据本来就在本机，绕开了 key 管理、网络故障和供应商 API 变更三类问题；
- 与硬件监控卡同构，复用现成的调度、快照、背压与可见性暂停，没有新增基础设施；
- 去重与窗口口径写进契约注释和回归测试，避免后续"看起来合理但是错的"数字。

## 后果

正面：

- 零网络、零凭据，隐私边界比天气更窄；
- 增量读取后每次 tick 约 5～7 ms，冷启动约 80～320 ms。

负面：

- 新增两个文件系统读取面，且读的是敏感文件，必须靠上面第 6 条约束守住；
- 用量口径依赖各家记录格式，格式变动会让读数失真而不是报错，靠跳过行计数器暴露；
- 两家口径不同意味着新增一家就要写一份新的解析与去重规则，这是刻意的：
  强行套用同一套口径正是产出"看似合理但错误"数字的方式；
- 费用估算依赖手工维护的价格表，会静默过期；缓解手段是价表自带核验日期，
  且无价模型不计入并显式报数，但过期的价格本身不会自我暴露。

## 门禁

若要提供请求级延迟与状态码，必须先有 ADR 决定是否引入本地 HTTP 代理——那是与本 ADR 不同量级的攻击面。

新增厂商前必须确认三件事，否则读数会静默出错：该厂商记录里哪个字段是权威计数、
同一次调用是否会被重复写入（以及据此的去重键）、以及它是否发布配额。
不得假设新厂商与已有两家中的任何一家同构。

**费用估算的门禁已于 2026-08-28 满足**，条件见第 9 节。
