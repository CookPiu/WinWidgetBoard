# ADR-0027：天气位置改为地点搜索，新增 Open-Meteo 地理编码端点

状态：Accepted
日期：2026-08-21
关系：修改 [ADR-0020](0020-open-meteo-weather-provider.md) 的「只有一个网络端点」结论；扩展 [ADR-0021](0021-weather-location-settings.md) 的位置设置流程

## 背景

天气位置此前要求用户**手工输入经纬度**。这是把一个数据库查询丢给了用户：没人记得自己城市的坐标，
去查一遍再抄回来既麻烦又容易抄错，而抄错的后果是天气静默地显示另一个地方——数值看上去完全正常。

要提供地点列表，只有两条路：内置离线城市表，或调用一个地理编码服务。

## 决策

1. 新增只读方法 `weather.locations.search`：入参是用户输入的地名，返回最多 8 个候选（名称、
   一级行政区、国家、国家代码、经纬度、时区）。
2. CoreBroker 通过 **Open-Meteo 地理编码端点**（`geocoding-api.open-meteo.com`）解析，
   与既有天气 provider 同一家供应商、同一个 `HttpClient`、同样无账号、无设备标识。
3. 设置对话框改为「搜索 → 从列表中选 → 保存」。经纬度**只读展示**，不再可编辑。
4. 搜索只在**提交时**发生（回车或搜索按钮），不做按键即搜：每次搜索都会离开本机，
   逐字符请求会把用户输入的内容成倍地送出去，远超他们想要搜索的那一次。
5. 该方法是唯一的异步命令，**不占用路由器的全局锁**，单独在管道循环里 await；
   它不读写任何共享状态，占锁只会让整个 Broker 排在一个远端主机后面。
6. 请求上界：查询 2～64 字符、去空白、拒绝控制字符；响应上界 64 KiB、8 秒超时、最多 8 条；
   缺少坐标或坐标越界的条目直接丢弃，不半填展示。
7. 落盘的仍然只有标签与经纬度（ADR-0021 未变）；搜索结果不缓存、不落盘。

## 理由

- 同一家供应商意味着不新增第三方信任关系，也不需要第二套超时/重试/隐私论证；
- 离线城市表需要选定数据集并在仓库中承担其许可（GeoNames 为 CC-BY 4.0，需要署名），
  而且只能覆盖被收录的城市，用户搜不到自己的区县时无路可走；
- 只读展示经纬度，使「究竟会把什么发给天气服务」保持可见，而不是藏起来。

## 后果

正面：

- 用户用地名就能设置位置，同名地点由「一级行政区 · 国家」区分；
- 保存的坐标来自服务端解析，不再可能抄错。

负面与约束：

- **多了一个网络端点，且第一次把用户输入的文本发到远端**。隐私边界因此扩大：
  在此之前离开本机的只有坐标和单位。`docs/09-security-privacy.md` 已相应更新；
- 搜索期间该连接上的其他请求会排队，最坏情况被推迟一次 8 秒超时。面板一次只有一个连接，
  取舍是接受这段延迟而不是为搜索另开一条连接；
- 搜索不可用（无能力、请求失败）与「没有匹配」在 UI 上是两种不同的提示，不能混为一谈。

## 放弃方案

- **内置离线城市表**：不联网、隐私边界不变，但需要在仓库中引入并署名一份数据集（许可尚未确定，
  见 ADR-0006），且覆盖面固定。若日后隐私要求收紧，这仍是首选替代。
- **两者都做（离线优先，搜不到再联网）**：UX 最好，但两条路径都要实现和验证，
  而隐私文档仍然要按「会联网」来写，成本翻倍收益有限。
- **按键即搜**：交互更顺，但把用户的每一次击键都变成一次外发请求。
- **在路由器锁内同步执行搜索**：实现最简单，但会让一次远端请求阻塞便签、布局和卡片订阅。

## 验证

- `UT-WEA-011`～`UT-WEA-017` 覆盖查询归一化与长度边界、结果解析与截断、
  缺失 `results` 视为空、无坐标行丢弃、候选到标签/描述的投影、同名行政区折叠、超长名称夹紧；
- 真实 Broker：`weather.locations.search` 对 `Hangzhou` 返回浙江/四川/萧山机场三条，
  无匹配返回空数组，单字符查询返回 `validation.invalid-argument`，能力列表含该方法；
- 真实桌面：设置对话框搜索 `Hangzhou` 后列出三条候选，选中后经纬度只读框同步更新。
