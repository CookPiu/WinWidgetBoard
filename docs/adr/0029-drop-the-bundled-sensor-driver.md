# ADR-0029：不分发内核传感器驱动，温度类读数保持「此电脑无法读取」

状态：Accepted
日期：2026-08-21
关系：取代 [ADR-0028](0028-system-monitor-scope-and-sensor-tiers.md) 第 7 条「传感器层的形态」；
ADR-0028 的其余结论（范围、两层划分、按需采样、两处独立配置、入口不做格式化）全部不变

## 背景

[ADR-0028](0028-system-monitor-scope-and-sensor-tiers.md) 把硬件读数分成公开 API 层与传感器层，
并明确写下一条开口项：**LibreHardwareMonitor 自带的重签名 WinRing0 能否在参考机的
HVCI + 驱动黑名单下加载，未验证；结果为否时应回到用户重新决定。**

现已验证。

## 验证结果

在参考机（Windows 11 26200，Intel Core Ultra 5 225H，HVCI 运行中，
`VulnerableDriverBlocklistEnable = 1`）上，以 **管理员** 运行 LibreHardwareMonitorLib 0.9.6：

| 项目 | 结果 |
| --- | --- |
| CPU 温度 | **无** |
| CPU 频率 | **无** |
| 风扇转速 | **无** |
| GPU 核心频率 | 800 MHz（不需要驱动的路径） |
| 硬盘温度 | 45 °C 真实读数 + 79/83 两个常量阈值（NVMe SMART，需管理员） |

结论：**提权不是瓶颈，驱动本身没有加载。** 该次运行没有安装任何服务，
系统日志里同时段的两条驱动安装事件属于用户已有的第三方监控软件在登录时安装自己的驱动。

同时确认：本机 `R0TrafficMonitor`（`TrafficMonitor.sys`）与 `RTCore64`（MSI Afterburner）
均处于运行状态。**这台机器允许内核驱动加载**，被拦下的是该库分发的那个具体驱动。

## 决策

1. **不实现 `src/SensorHost`，不引入 LibreHardwareMonitorLib，不新增第四个进程。**
   `Directory.Packages.props` 与锁文件保持只有微软与测试框架包。
2. **不分发任何 WinRing0 系驱动**，包括改名或换签名以绕开黑名单的变体。
3. 温度、风扇、CPU 频率四项保留在指标表中，状态恒为 `unavailable`，
   UI 文案是「此电脑无法读取」而不是「本产品不支持」——措辞指向这台机器，
   因为换一台带独立显卡的机器，GPU 温度可能经 NVAPI 在不需要驱动的情况下读到。
   （**其中 CPU 频率一项已由 [ADR-0031](0031-cpu-clock-from-per-core-counters.md) 改为可读**：
   它并不需要驱动，只是此前用错了计数器实例。本条对温度与风扇继续成立。）
4. 硬件监控以公开 API 层的 8 项交付，不再等待第二层。
   （项数已由 [ADR-0031](0031-cpu-clock-from-per-core-counters.md) 增至 9 项。）

## 理由

**为什么不改名分发。** TrafficMonitor 的驱动能加载而 LibreHardwareMonitor 的不能，差别很可能
就在于前者不匹配黑名单的特征。WinRing0 上黑名单的原因是它提供任意物理内存读写，
任何进程都能借它提权。把这样一个驱动随安装包送到别人机器上，等于替每一位用户装了一个提权后门；
为了绕过一份安全黑名单而改名，更是把这件事从疏忽变成有意。这条线不越，
与功能优先级无关。

**为什么不为硬盘温度单独建提权助手。** 唯一新增的读数是一项硬盘温度，
而它根本不需要这个第三方库——直接 P/Invoke NVMe SMART 即可，同样要管理员。
也就是说这个依赖买不到任何只有它能提供的东西，却要付出第四个进程、第一个第三方运行时依赖、
以及一次 UAC 的代价。

**为什么不改用第三方监控软件的共享内存。** 实测 MSI Afterburner 的 `MAHMSharedMemory`
在本机非提权可读，但其中**没有 CPU 温度**（该软件在本机未采集）。HWiNFO 的共享内存确实包含
CPU 温度，但要求用户安装并常驻 HWiNFO——那只是把常驻一个第三方监控软件换成常驻另一个，
用户已就此选择放弃。

## 后果

- `SYS-002`（普通用户运行）不再受任何威胁：整个功能无提权路径；
- 进程数保持三个，[ADR-0002](0002-split-process-architecture.md) 未被打破；
- 想要 CPU 温度的用户继续使用现有第三方组件，与本产品并存不冲突；
- 若将来目标机器带独立显卡，GPU 温度可能在不引入驱动的前提下经厂商 API 读到，
  届时是一个独立的、小得多的决定，不需要推翻本 ADR 的第 2 条。
