# ADR-0028：重新纳入硬件监控，并把传感器读数分成两层

状态：Accepted
日期：2026-08-21
关系：修改 [ADR-0022](0022-lightweight-core-strategy.md) 的「核心五项」结论（系统监控由延期改为纳入）；扩展 [ADR-0024](0024-background-provider-keepalive.md) 的后台刷新策略

## 背景

用户希望用本产品取代常驻的第三方任务栏监控组件，要求硬件监控同时具备**卡片形态**和**任务栏形态**，
两处都能自定义显示项、顺序和详细度，并明确要求包含**温度、风扇与频率**。

[ADR-0022](0022-lightweight-core-strategy.md) 把系统监控列为延期项，并要求任何恢复都需要明确再批准。
本 ADR 就是那次再批准的记录。

实测参考机（Windows 11 26200，Intel Core Ultra 5 225H）得到的三条事实决定了方案形状：

- GPU 占用与显存可由 PDH 计数器读出，普通用户权限即可；
- `MSAcpi_ThermalZoneTemperature` 对普通用户**拒绝访问**，且即便提权也只有芯片组温区，不是核心温度；
- 本机 **HVCI（内存完整性）正在运行**，`VulnerableDriverBlocklistEnable = 1`。

## 决策

### 1. 范围

核心五项变为**核心六项**，新增「硬件监控」。`docs/01-product-requirements.md` 的延期清单相应移除该条。
这仍不重新开放计时器、待办、剪贴板、日历、插件、账号与云同步。

### 2. 读数分两层

| 层 | 来源 | 权限 | 状态 |
| --- | --- | --- | --- |
| 公开 API 层 | `GetSystemTimes`、`GlobalMemoryStatusEx`、`NetworkInterface`、`DriveInfo`、PDH | 普通用户 | 已实现 |
| 传感器层 | 第三方内核驱动库（LibreHardwareMonitor） | 需要管理员安装一次 | 未实现 |

公开 API 层覆盖 CPU 占用、内存、GPU 占用与显存、磁盘活动与占用、网络上下行共八项。
温度、风扇、CPU 频率四项属于传感器层，在其到位前一律报 `unavailable`。

**缺读数就说缺读数，不猜。** 每个指标都带状态（`ready` / `pending` / `unavailable`），
UI 显示「此电脑无法读取」而不是 0 或占位数字。

### 3. CPU 频率归入传感器层

用户态测不准，这是实测结论而不是保守估计：

- `\Processor Information(_Total)\Processor Frequency` 在参考机上恒定返回 **1.33 GHz**，
  而同一时刻第三方组件（读 MSR）显示 **4.19 GHz**；
- `% Processor Performance × 注册表 ~MHz` 得到 **8.18 GHz**——因为 `~MHz` 记录的是开机时的频率，
  不是基准频率。

混合架构 CPU 上这两条路都不成立。**一个和任务管理器明显对不上的数字，比诚实的空缺更糟**，
因此频率与温度同层等待。

### 4. 采样按需进行

Provider 以 **2 秒**节奏采样，但**只在有人看时才采**：

- 卡片在面板中可见（走既有 `ProviderRefreshVisibilityRegistry`）；或
- 任务栏入口在近 10 秒内索要过摘要（`sysmon.summary.get` 本身即需求信号）。

两者皆无时完全休眠。从休眠恢复后丢弃增量基线，第一拍显示 `pending` 而不是一个跨越整个休眠期的平均值。

这是对产品原则 5「按需运行」的直接压力，缓解手段就是上面这条，其实测占用必须记录在状态页。

### 5. 卡片与任务栏各自独立配置

两份列表，各自最多 8 项，顺序即列表顺序。任务栏窄、卡片宽，共用一套配置总会让其中一边被迁就。

### 6. 入口不做格式化，也不做本地化

Broker 交付**已经排好版的字符串**，与 `weather.summary.get` 同样的纪律。
入口的短标签（`CPU`、`MEM`、`GPU`、`VRAM`、`DISK`、`FAN`）在本产品发布的两种语言中写法相同，
网络方向由箭头图形表达，因此任务栏上不出现任何需要翻译的文字。

### 7. 传感器层的形态（尚未实现，但边界现在就定下）

- 第三方依赖只落在一个新项目 `src/SensorHost` 里，CoreBroker 保持无第三方运行时依赖；
- 提权部分是**可选的、单独安装的**：不装也能用，温度等项显示「需要传感器服务」；
- 因此 `SYS-002`（普通用户运行）对安装与基础运行仍然成立；
- 提权进程不在 LauncherHost 的 job object 内，[ADR-0026](0026-launcher-owned-process-tree.md)
  的「不留孤儿」保证覆盖不到它，所以它必须在客户端断开且无人重连时自行退出。

## 理由

**为什么不直接用第三方监控软件的共享内存。** 可行且实测可读（MSI Afterburner 的 `MAHMSharedMemory`
在参考机上非提权即可打开），但那要求用户始终运行另一个软件。用户选择了自带驱动库的方案，理由是
体积小、占用低、适合分发。

**为什么温度不能先用 WMI 顶一下。** `MSAcpi_ThermalZoneTemperature` 普通用户拒绝访问，
提权后也只有芯片组温区，与用户期望的 CPU/GPU 核心温度不是一回事。给出一个来源不同、含义不同的数字，
比不给更糟。

**为什么 2 秒而不是 1 秒。** 用户选定。肉眼几乎看不出差别，采样与重绘成本减半，
而网络速率这类累积量在 2 秒窗口上反而更稳。

## 后果

- 引入本项目第一个第三方运行时依赖（传感器层落地时），`Directory.Packages.props` 与锁文件随之变化，
  依赖许可表需增加 MPL-2.0 一行；
- 进程数由三变四（仅在用户安装传感器服务时）；
- **未验证且必须先验证的一条**：LibreHardwareMonitor 自带的重签名 WinRing0 在本机
  HVCI + 驱动黑名单下能否加载。传感器层开工的第一步是这个验证，结果为否时应回到用户重新决定，
  而不是继续投入。参考机上第三方组件当前确实显示着 CPU 温度与频率，说明该路径在本机可行，
  但那不等于本产品自带的驱动也能通过。

## 备选方案

- **继续延期**：与用户明确诉求冲突，且用户已就该冲突再次确认。
- **整个应用提权运行**：直接违反 `SYS-002`，并让持有 SQLite 与网络访问的 Broker 长期运行在管理员上下文，
  安全姿态不可接受。
- **只做使用率、不做温度**：用户已明确拒绝该折中。
