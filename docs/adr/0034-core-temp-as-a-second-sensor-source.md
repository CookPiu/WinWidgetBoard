# ADR-0034：温度源改为多来源，新增 Core Temp

状态：Accepted
日期：2026-09-01
关系：扩展 [ADR-0033](0033-hwinfo-shared-memory-sensor-source.md) 第 1 条（单一来源）与第 3 条
（只认全局命名空间）；ADR-0033 其余结论与 [ADR-0029](0029-drop-the-bundled-sensor-driver.md)
「不分发也不加载任何内核驱动」全部不变

## 背景

[ADR-0033](0033-hwinfo-shared-memory-sensor-source.md) 把温度与风扇接到 HWiNFO 的共享内存上，
并在后果里记下了一条：**HWiNFO 免费版的共享内存有 12 小时限制，到期自动关闭且需手动重新勾选。**

对自己用的机器这是个小麻烦，对一个要分发出去的工具则是硬伤——不能让产品的一项能力
依赖于用户每天手动去另一个程序里重新打勾。用户据此要求换一个不受此限的来源。

同时排除的还有 MSI Afterburner 与 TrafficMonitor：前者在参考机上实测不发布任何温度或转速
（见状态页的四条否定路径），后者根本没有对外发布读数的接口，只能靠加载 WinRing0 自己显示。

## 决策

1. **温度与风扇的来源不再是「HWiNFO」这一个，而是一组**。当前两个：
   - **HWiNFO**：CPU 温度、GPU 温度、风扇转速；
   - **Core Temp**：**只有 CPU 温度**。免费、体积小、无时限，共享内存结构有官方 SDK 文档。
2. **同一项读数上 HWiNFO 优先**：它的块里每条读数都自带标签与所属传感器名，选中的是哪一个传感器
   可以说清楚；Core Temp 只给一组按核编号的浮点数，作为 CPU 温度的补位。
3. **「有没有源」改为逐项判断**，不再是一个全局布尔。只跑 Core Temp 的机器，CPU 温度**有**源、
   GPU 温度与风扇**没有**——把它算成「源在运行」会让后两项显示「此电脑无法读取」，
   等于告诉用户这台机器读不到，而其实换个源就能读。
4. **命名空间按来源各自决定，但只允许「全局优先、本地兜底」这一个方向。**
   HWiNFO 发布在全局命名空间，因此仍然只认全局（ADR-0033 第 3 条不变）。
   Core Temp 不带命名空间前缀发布，提权时落在全局、否则落在会话本地，因此两个名字都试，
   **先全局后本地**。反过来（全局失败才回落本地，或本地优先）才是攻击面：
   会话本地命名空间任何进程都能创建同名段。
5. **文案改为「需 HWiNFO/Core Temp」**，不再只点名一个。

## 理由

**为什么不干脆只用 Core Temp。** 它不给 GPU 温度也不给风扇，换掉 HWiNFO 等于砍掉两项读数。

**为什么取最热的那颗核作为 CPU 温度。** Core Temp 给的是逐核温度，没有封装温度。
混合架构上八颗能效核闲着、一颗性能核满载时，平均值不描述芯片上的任何一点；
最热的那颗才是要触发降频的那颗，也是其他工具口中的「CPU 温度」。

**为什么必须处理块里的两个标志位。** Core Temp 可以显示华氏度，也可以显示「距 TjMax 还有多少度」。
两者都在块里只是一个字节的开关，读错的后果不是报错而是一个看起来合理的假数字——
忽略华氏度标志会把 60 °C 显示成 140；忽略余量标志会得到一台越忙越凉的电脑。
顺序也是固定的：先在同一单位内还原余量，再换算单位。

**为什么不靠 poll 时钟判活。** Core Temp 的块里没有时间戳，而共享段因为我们持着句柄不会随
Core Temp 退出而消失。因此改为定时丢句柄重开：Core Temp 已经退出时，段随最后一个句柄消失，
下一次打开自然失败；还在运行则只是每 30 秒多一次打开调用。

## 后果

- 仍然不新增进程、不新增第三方运行时依赖、不需要提权、不分发任何驱动；
- 用户可选的温度源从一个变成两个，其中 Core Temp 没有时限，可以作为默认推荐；
- 「需要用户装点什么」这件事本身没有消除。要在零依赖的前提下读到 CPU 温度，
  仍然只有自签内核驱动一条路，那是一个独立且更贵的决定，本 ADR 不涉及；
- 参考机既没有 HWiNFO 也没有 Core Temp，**两个来源的真实块解析都尚未在真机上验证**，
  跑过的都是测试自己写出的合成块。
